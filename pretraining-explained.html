Pretraining explained: what happens when you run it

When you type npm run train:full, a TimesNet encoder learns from about 304,000 unlabeled windows (benign + GridSybil, 64 messages × 13 features each). It never sees an attack label. Each training step takes 256 windows and builds three versions of them: one with rows hidden, one shifted / stretched / cropped, and one with a physics violation we inject. The encoder makes three forward passes, five losses are computed, scaled and summed, and one AdamW update follows. After every pass over the data (an epoch), a label-free check set decides whether to save best.pt and whether to stop. This page follows that loop from data to checkpoint, with the real settings from src/model/benign_gridsybil/timesnet/.

338,001 train windows→ −10% vehicles → ≈ 304k→≈ 1,190 batches × 256→ 3 passes → 5 losses→1 joint loss→ AdamW →best.pt
Nothing is trained yet. Every setting on this page comes from the code. The few measured numbers are labelled at initialisation or from a stopped test run (batch 128, steps 1–400). They show how the code behaves, not results. How the encoder itself works (embedding, TimesBlocks, H and z) is on Encoder Shapes.

The label firewall

LabelFirewall checks every file path before it is opened. It allows only train/ (or a pretrain_val/ folder, if one exists) and only feature shards named part-NNNNN.json. A request for an _info file (which holds labels) or anything under test/ raises PermissionError and the run stops. env.json records "label_files_opened": 0.

Why the check set comes from train vehicles

Early stopping needs a validation number, but the test split is reserved for the final evaluation. So 10% of the train vehicles are set aside. They are chosen by vehicle, not by window: all windows of one sender land on the same side, so the check set measures what the model does on vehicles it has not seen.

Scaling at load time (D13)

The stored files hold train z-scores. Three features have a very long tail because GridSybil ghosts can sit kilometres away: claimed_pos_x, claimed_pos_y and range. When the data is loaded they are re-scaled with the median and the IQR (interquartile range) of the train real rows. Above |z| = 5 the values are squeezed with a logarithm. Their order is kept and the step can be undone exactly.

z = (raw − median) / IQR (median, IQR from train real rows only) z' = z if |z| ≤ 5 z' = sign(z) · (5 + log1p(|z| − 5)) if |z| > 5 (soft tail)

The other 10 features keep their train z-scores. The stored files are not changed. The median, IQR and soft-tail setting go into env.json → scaling.

From windows to batches

One epoch = every training window exactly once, in batches of 256 → ≈ 1,190 steps.

Length-bucketed batches (D14)

A TimesBlock runs its FFT and period folding once for each distinct window length in a batch. A random batch of 256 holds about 60 different lengths. A length-bucketed batch holds 2–3. The batches of one epoch are built like this:

shuffle all ≈ 304k→stable sort by real rows →cut into 256s→shuffle batch order

Shuffling first and using a stable sort means windows of the same length are still in random order. Shuffling the batch order then mixes short and long batches through the epoch. The random generator is seeded with seed + epoch, so the order is the same every time. A resumed run picks up exactly where it stopped.

Side effect: inside a batch, the contrastive negatives have almost the same length as the anchor, so length cannot help tell them apart. That is good: the encoder should not learn window length as a shortcut.

The prefetch thread

BatchPrefetcher runs a background thread that copies the next batches (indices → 256 × 64 × 13 + mask) out of memory while the Apple GPU (MPS) trains on the current one. It keeps up to prefetch_batches = 3 batches ready in a queue, so the GPU does not wait for the CPU.

One training step

One batch of 256 windows, three forward passes through the same encoder, five losses, one backward pass.

PassInputEncoder output usedHeadLoss
1view v1, with 25% of real rows hidden (mask token)H 256 × 64 × 128 and z₁ 256 × 128reconstruction (on H)MSE on hidden rows
2view v2, nothing hiddenz₂ 256 × 128projection (on z₁ and z₂)NT-Xent
3the clean window with an injected violation in half the windowszᵢ 256 × 128P1, P2, P3 (on zᵢ)3 × BCE

The two views

Both v1 and v2 come from the same window, each with its own random draw of three changes. Each change keeps the motion physically possible:

  • Common shift 3–5 m: sender and receiver positions move together, so range and bearing stay the same.
  • Time stretch s ∈ [0.95, 1.05]: velocity × s, acceleration × s², Δτ ÷ s. Positions stay put, so Δposition = v·Δτ still holds.
  • Contiguous crop: keep one unbroken run of 80–100% of the real rows. It is moved to the start and the rest becomes padding.

Hiding rows on v1

For each window, a coin flip picks one of two ways to hide rows: exactly 25% of the real rows at random, or one block of 20–30%. The hidden rows are replaced by the mask token, a learned vector of 13 numbers (model.mask_token). Padding rows are never hidden.

The injected copy

Only windows with at least 4 real rows are eligible. In half of them, one violation is injected from a random row to the end:

  • P1 position jump: the claimed position jumps 50–150 m and stays shifted. Range and bearing are recomputed to match.
  • P2 speed scaled: the claimed velocity is multiplied by 2–3 or by 0.2–0.5, but the positions do not change. Needs a mean speed ≥ 2 m/s.
  • P3 sharp turn: the claimed velocity and acceleration are rotated by 90–180°. Needs speed ≥ 2 m/s.

For a slow window, a draw of P2 or P3 becomes P1. The target "was violation k injected?" comes from our own injection. It is never an attack label (D4).

The step, from losses.py · Objective.__call__ (shortened)

# x: (256, 64, 13) normalised windows, mask: (256, 64) bool real rows
v1, m1 = self.augment(x, mask, gen)          # view 1: shift, stretch, crop  (256, 64, 13)
v2, m2 = self.augment(x, mask, gen)          # view 2: its own random draw
hidden = self.masker(m1, gen)                # (256, 64) bool: 25% random or one 20-30% block

# pass 1: masked view -> reconstruction
h1, z1 = model.encoder(model.hide(v1, hidden), m1)   # H (256, 64, 128), z (256, 128)
pred = model.recon_head(h1)                          # (256, 64, 13)
losses["recon"] = MaskedOps.masked_mse(pred, v1, hidden)   # hidden rows only

# pass 2: clean view -> contrastive
_, z2 = model.encoder(v2, m2)                        # (256, 128)
keep = (m1.sum(1) >= 4) & (m2.sum(1) >= 4)          # windows with >= 4 real rows in both views
p1, p2 = model.proj_head(z1[keep]), model.proj_head(z2[keep])   # (m, 128), unit length
losses["nce"], n_masked = nt_xent(p1, p2, 0.1, groups[keep])

# pass 3: injected copy -> physics heads
xi, targets, valid = self.inject(x, mask, gen)       # targets (256, 3) in {0, 1}
_, zi = model.encoder(xi, mask)                      # (256, 128)
logits = model.physics_heads(zi)                     # 3 × (256,)
for j, name in enumerate(("p1", "p2", "p3")):
    losses[name] = F.binary_cross_entropy_with_logits(logits[KEY[j]][valid], targets[valid, j])
Transformer view
  • Pass 1 is BERT's masked-token objective for numbers: a learned [MASK] vector, then a regression loss on the masked positions only.
  • Pass 2 is SimCSE / SimCLR: two views of one window go through the same encoder and should land close together.
  • Pass 3 is a small multi-label classifier on the pooled vector. Its labels come from our own injections.

The five losses

What each loss asks of the encoder, its formula and what "good" looks like.

Reconstruction (MSE on hidden rows)

The loss asks: "Fill in the rows I hid." It is the mean squared error over the 13 features of the hidden rows only. Visible rows and padding do not count.

L_rec = mean over hidden real rows r and features f of (pred[r, f] − v1[r, f])²

Good: it falls well below the linear-interpolation baseline, which fills each hidden row with a straight line between the nearest visible rows. At initialisation (measured) the check-set value is 1.03 and the interpolation baseline is 0.21. The model has to get below 0.21 to be doing more than drawing straight lines.

Contrastive (NT-Xent, τ = 0.1)

The loss asks: "Of all windows in this batch, which one is the other view of this window?" The m kept windows give 2m projections. For each one, the other view is the positive and every other projection is a negative. It is a softmax cross-entropy over cosine similarities divided by τ.

ℓ(i) = −log [ exp(cos(pᵢ, pᵢ⁺)/τ) / Σ_{k ≠ i, k not masked} exp(cos(pᵢ, p_k)/τ) ] L_nce = mean over 2m

False negatives are masked (D13): windows from the same broadcasting pseudonym in the same run are copies or crops of the same broadcasts, so they are taken out of each other's negatives. All GridSybil ghosts use pseudonym 1, so they count as one group per run. The grouping uses only what a receiver can see (run + pseudonym), never the true sender. Good: it falls steadily. From a stopped test run (batch 128, steps 1–400): 2.29 → 0.17. Very low values early on can also mean the task is too easy, so read it together with the collapse monitors.

Physics heads P1, P2, P3 (binary cross-entropy)

Each head asks: "Was violation k injected into this window?" A head reads z of the injected copy and outputs one logit. The loss is BCE-with-logits over the eligible windows. About 1 in 6 windows is positive for each head (half are injected, split over three types; P1 a bit more, because slow windows get P1).

L_Pk = − mean over valid windows of [ y log σ(s) + (1 − y) log(1 − σ(s)) ]

Good: AUROC on the check set rises well above 0.5. At initialisation (measured) it is ≈ 0.47–0.53, which is chance. From a stopped test run (batch 128, steps 1–400): P2 / P3 losses fell to 0.15–0.27, while P1 stayed at ≈ 0.53–0.67 and was not yet learning.

From five losses to one number

Each raw loss is divided by its own scale, multiplied by its weight λ, and the five results are added up.

L = 1·L_rec/s_rec + 0.3·L_nce/s_nce + 0.3·L_P1/s_P1 + 0.3·L_P2/s_P2 + 0.3·L_P3/s_P3
  • Scales s: the running mean of each raw loss over the first 200 steps. After that they are frozen for the rest of the run (and saved in the checkpoint).
  • Why divide: the raw losses live on different scales (in the stopped test run, batch 128, the first values were MSE 1.18 and NT-Xent 2.29; a BCE head at chance gives log 2 ≈ 0.69). After dividing, each term is ≈ 1 at the start, so λ really sets the balance (D7).
  • Why freeze: if the scales kept following the losses, every term would stay near 1 and the joint loss could not go down. Freezing turns L into a fixed yardstick. That makes val_joint comparable across epochs, which early stopping needs.
  • λ: reconstruction 1, the others 0.3 (λ_nce ∈ {0.1, 0.3, 1} is the planned sweep: --lambda-nce).
Animation · five losses → one joint loss

From losses.py · LossScales and Objective.joint

class LossScales:
    def update(self, raw, step):            # raw: {"recon": 1.18, "nce": 2.29, ...} (floats)
        if self.frozen: return
        for k, v in raw.items():
            self.sum[k] += v; self.count[k] += 1
        if step + 1 >= self.warmup:             # warmup = 200 steps
            self.frozen = True

    def scale(self, name):                    # running mean, then frozen
        return max(self.sum[name] / self.count[name], 1e-8)

def joint(self, losses, scales):              # losses: 5 scalar tensors
    weight = {"recon": 1.0, "nce": 0.3, "p1": 0.3, "p2": 0.3, "p3": 0.3}
    return sum(weight[k] * v / scales.scale(k) for k, v in losses.items())   # scalar

The update

Backward pass, gradient clipping, one AdamW step and one learning-rate step. The encoder and the heads all change a little.

  • Backward: gradients of L flow back through every head into the shared encoder. All three passes add to the same encoder weights.
  • Clip: if the overall gradient norm is above 1.0, all gradients are scaled down to norm 1.0. One unusual batch cannot throw the weights far. The norm measured before clipping is logged as grad_norm.
  • AdamW: lr 1e-3, weight decay 0.05 (decoupled: each weight shrinks a little every step). It updates 2,402,461 parameters: the encoder's 2,301,312, the heads and the 13-number mask token.
  • Learning rate: linear warm-up over 500 steps up to 1e-3, then cosine decay to 0 over the planned steps (max epochs × steps per epoch ≈ 23,800). If the run stops early (early stopping, time or memory), the LR is still part-way down the curve.
  • Seeding: the random draws of a step (views, masks, injections) use the seed seed · 1,000,003 + step, so a resumed run makes the same views again.

From train.py · Trainer._train_step and _lr_factor

gen = torch.Generator().manual_seed(s.seed * 1_000_003 + self.step)    # same views on resume
losses, extra = self.objective(self.model, x, mask, gen, groups)      # 5 raw losses
self.scales.update({k: float(v) for k, v in losses.items()}, self.step)
loss = self.objective.joint(losses, self.scales)                     # scalar
if not torch.isfinite(loss):                                          # NaN / inf: save and stop
    self._save("last.pt"); raise FloatingPointError(...)
self.opt.zero_grad(set_to_none=True)
loss.backward()                                                       # grads for 2,402,461 params
grad_norm = nn.utils.clip_grad_norm_(self.model.parameters(), 1.0)    # norm before clipping
self.opt.step()                                                       # AdamW(lr 1e-3, wd 0.05)
self.sched.step()                                                     # warm-up 500, then cosine

def _lr_factor(self, step):                                          # multiplies lr = 1e-3
    if step < 500: return (step + 1) / 500
    progress = (step - 500) / (self.total_steps - 500)
    return 0.5 * (1 + math.cos(math.pi * min(1.0, progress)))

Logging

Every 50 steps (and at step 1), one line goes to metrics.jsonl and the console with: joint, recon, nce, p1–p3, grad_norm, lr, seconds per step, memory, same_link_pairs (pairs of windows from the same link in the batch) and nce_masked_pairs (negatives removed as false negatives).

End of each epoch: evaluate, save, maybe stop

After every epoch the model runs on the check set without updating. It still uses no labels.

What is evaluated

A fixed subset of 8,192 check-set windows, in batches of 512, with fixed views: the same masks, crops and injections every epoch. A change between epochs therefore comes from the model, not from the random draws. A clean pass of each window also gives a z for the monitors.

Checkpoints and stopping

  • best.pt: saved when val_joint improves on the best so far by more than 1e-4.
  • last.pt: saved after every epoch, and when the run stops. This is what --resume reads.
  • Early stopping: after 5 epochs in a row without improvement.
  • Budgets: max 20 epochs. Time: 8 h (npm run train) or 30 h (npm run train:full), checked after every step. Memory: mem_gb = 22; the run stops cleanly once the process passes 95% of it.
  • A run stopped by a budget runs one more evaluation (stop_…) and saves best.pt if that evaluation improved.

Pre-flight checks (train:check, and at the start of every run)

  • Filling the padding rows with large random numbers changes no loss and no z (Δ = 0).
  • Scaling round-trip (normalise → raw → normalise) is exact to ≤ 1e-3.
  • Masking, injection and augmentation touch real rows only. No window grows, and windows with < 4 real rows are never injected.
  • Parameter counts: encoder 2,301,312, total 2,402,461.

Stopping and resuming

  • Ctrl-C stops at once. last.pt is from the last finished epoch, so the current epoch's steps are lost.
  • npm run train:resume -- src/runs/pretraining/benign_gridsybil/T64/<run_id> reloads model, optimiser, scheduler, scales, step, best and patience, and continues with the same batch order and views. --max-hours can be raised on resume.

Questions, answered simply

Click a question to open the answer.

Why three forward passes, not one?

Each objective needs a different input. Reconstruction needs rows hidden. Contrastive needs a second, unhidden view to compare with. The physics heads need a copy with a violation injected. Hiding rows in the contrastive view would let it match on the mask pattern, and injecting into the masked view would mix two tasks. So the same encoder runs three times and the gradients of all three passes add up in one backward pass. A step therefore costs about 3× one encoder pass.

Why freeze the loss scales after 200 steps?

Scales are needed so that a loss of size 5 (NT-Xent) does not drown one of size 0.7 (BCE). If they kept updating, each term would be divided by its own current value and stay ≈ 1: the joint loss would be flat and could not pick a best epoch. Frozen scales are a fixed yardstick: val_joint falls only if the losses really fall.

Why mask "false negatives" in NT-Xent?

One broadcast is heard by many receivers, and one link gives several crops. Two windows of the same pseudonym in the same run can therefore be almost the same data. Pushing them apart as negatives would teach the encoder to separate identical motion. Those pairs are left out (D13), and nce_masked_pairs in the log shows how many. All GridSybil ghosts use pseudonym 1, so they form one group per run.

Why take the check set from train, not from test?

The check set chooses best.pt and when to stop, so it shapes the model. If it were the test split, the final test numbers would be optimistic (RULE 3). It is carved by vehicle, so no vehicle is in both parts, and it is read without labels.

Why length-bucketed batches? Is that still random?

Speed: the FFT / period step runs once for each distinct length, about 60 per random batch and 2–3 per bucketed batch (D14). It is still random: windows are shuffled within each length, the batch order is shuffled every epoch, and every window is seen once per epoch. A bonus is that negatives share the anchor's length, so length cannot be used to tell them apart. length_bucketed = False brings back random batches.

What if P1 stays flat?

In the stopped test run (batch 128, steps 1–400) P1 had not started learning (loss ≈ 0.53–0.67) while P2 / P3 had. That early in a run it is not alarming. A 50–150 m jump that stays shifted changes the positions, range and bearing, but z is an average over the window and may hide a single step change. If auroc_p1 stays ≈ 0.5 for several epochs, report it as found and look at P1 per window length. Do not change the injection to make the number look better (RULE 1); any change to the design is a decision to record.

What if the length probe stays high?

At initialisation z already predicts the window length with R² 0.96, partly because short and long windows look different. If it stays near 1 while the other signals improve, the encoder may be leaning on length. Length alone separates the classes only weakly (AUC 0.535 on test), but later probes should then be reported within length bands, and the shortcut should be named in the thesis.

What if the loss becomes NaN?

The step checks torch.isfinite(loss). On NaN / inf it saves last.pt and stops with FloatingPointError. Look at the last logged grad_norm and the raw losses. Usual fixes are a lower learning rate or finding a bad window. Start a new run with the change, and record it in config.json.

How long does it take?

Unknown at the current settings until npm run train:smoke is run. For reference, the stopped test run (batch 128, random batches) took ~1.65 s/step ≈ 65 min per epoch. Length-bucketed batches of 256 should be much faster per epoch. With early stopping the run may end well before 20 epochs.

Which file do I hand on after pretraining?

best.pt. Only its "encoder" weights are used later. The heads and the mask token are discarded. Keep the run folder whole: config.json and env.json are what make the result reproducible (RULE 4).
