  • Receiver's own GPS — where the receiving car really is, latest fix at receive time.

Design decisions · relative geometry

Range and bearing: where the claim sits relative to me

  • dx, dy = claimed position − receiver's own position.
  • range = √(dx² + dy²) in metres; bearing θ = atan2(dy, dx).
  • Range separates DoSRandom: p50 743 m vs benign 81 m.
  • One angle, wrapped to (−π, π] — not sin/cos — so the feature count stays 13.
Range and bearing replace the two time-of-day columns: they carry information about the message, not about the clock.
Speaker note: a real receiver can always compute these two numbers — its own GPS plus the sender's claim. The ±π jump in the angle is the trade-off of using one angle instead of sin/cos.
Design decisions · timing

Δτ: how long since I last heard this pseudonym

log_dtau = log(max(Δτ, 0.001 s)), computed per receiving car and per sender pseudonym.

  • Benign: about 1 s (log ≈ 0); p99 gap 7–9 s when messages are missed.
  • GridSybil: bursts — 15% of gaps are under 0.5 s.
The first message of a link has no previous one → log_dtau = null. The message is kept; in the encoder input it becomes 0 (the train mean).
Speaker note: the 0.001 s floor keeps the log finite when two copies arrive at the same time. Δτ is the only timing signal the model gets — the clock time itself is never an input.
Design decisions · exclusions

What is never an input, and why

Time of day
It alone separates the groups: sin(time) ∈ [0.70, 0.97] for 0709 vs [−0.87, −0.50] for 1416. The 0709 ↔ 1416 transfer test would be meaningless.
True sender id
The simulator's real identity of the sender. A real receiver never sees it; it would reveal who the attacker is.
*_noise fields
Simulator bookkeeping of the sensor noise added — not something a car can measure.
Ground-truth positions
The ground-truth files (1.7 GB) are never read for features.
The sender id is used only outside the features: to split the shared ghost pseudonym 1 into links, and as the key of the vehicle split.
Speaker note: the rule is "only what a real receiving car could know". Anything that is simulator truth or a clock shortcut stays out of the 13 columns.

Leakage · shortcuts

Shortcuts we checked

A feature that predicts the label or the scenario by itself would let the model cheat.

Time of day — removed
sin(time) is in [0.70, 0.97] for 0709 and [−0.87, −0.50] for 1416: perfect separation. It would break the 0709 ↔ 1416 transfer test, so it is never an input.
Window length — possible shortcut
Windows of 1–3 messages: 13.9% of benign (18,509) vs 20.2% of GridSybil (49,242). Short windows lean GridSybil, and the mask reveals the length. Option: a floor (min_messages, e.g. 4).
Sequence length — weak, not an input
On the first (network-wide pseudonym) sample set, length alone gave AUC 0.551, just outside the ±0.05 band. Length is never a feature, but the mask carries it.
Speaker note: For each suspicious feature we trained a one-feature probe and looked at its AUC; 0.5 means it carries no label information. Time of day was a perfect separator of the two scenario groups, so it was replaced by range and bearing. Length is not a feature, but through the mask the encoder can see how many real messages a window has, and very short windows are more often GridSybil; a length probe on the new windows, or a minimum of 4 messages, would settle it.
Leakage · pseudonyms

Pseudonym switching and ghost pseudonym 1

How attackers use pseudonyms decides which attacks can even reach a 64-message encoder window.

illustrative lengths
  • DataReplay / DoS switch pseudonym every 1–2 messages: 0 DoS links reach 64; DataReplay 0–1.
  • GridSybil ghosts all use pseudonym 1: 42,864 links come from it.
Consequence 1: DataReplay and DoS are absent from the encoder input (benign + GridSybil only). How to include them is open.
Consequence 2 (F13, open): pseudonym 1 is split per ghost using the true sender id, privileged information. Part of the GridSybil windows come from it.
Classes in the encoder input: ≈ 65% GridSybil / 35% benign, so use class weights and macro metrics.
Speaker note: A link is everything one car heard from one pseudonym, so attackers that change pseudonym every message never build a 64-message history, and they drop out of Stage 1 entirely. The opposite problem is GridSybil: all ghosts share pseudonym 1, and we separate them using the true sender id, which a real receiver would not know, so those windows need a decision.
Pipeline · overview

Three notebooks turn raw logs into encoder input

Raw VeReMi is mirrored file by file, a read-only EDA picks the window sizes, then every link is cropped into masked windows of at most 64 messages.

input_representation keeps the receiver's view exactly as recorded: every received copy, same folder tree (2.9 GB).
eda_window_size reads only: link lengths, a no-padding T sweep and class balance per T. Writes nothing.
encoder_input_T64 builds what the encoder reads: every message in a window padded to 64 rows, with a mask (1.8 GB).
Speaker note: The first notebook mirrors the raw data without throwing anything away. The EDA notebook only reads; it showed that a fixed T without padding loses most links. The third notebook crops every link into windows of at most 64 messages, pads each to 64 rows and stores a mask, so every message reaches the encoder in one fixed shape. All code lives in notebooks under src/ (pipeline/, eda/, model/); src/README.md explains the layout. Benign + GridSybil is the first trial of the whole pipeline; the other attacks follow.

Pipeline · windowing

Crop, pad to 64, mask: every message in a window

Each link is cut into consecutive pieces of at most 64 messages; each piece is padded at the end to 64 rows, and a mask marks the real rows. The encoder always sees 64 × 13.

real messagespaddingmask = 1mask = 0
Speaker note: Nothing is thrown away: the 150-message link gives two full windows and one 22-message window padded to 64, and a 5-message link still gives a 64-row window with 59 padding rows. Every window has the same shape, so batches are standard and the mask tells the encoder which rows are real.
Pipeline · design choice

Why crop, pad to 64 and a mask

Links are mostly short (benign median 14, GridSybil 11 messages), so any single fixed length either loses data or fills the input with padding. We accept the padding for one fixed shape.

OptionEffect on the data
Fixed T = 64, no paddingkeeps 5% of links / 21% of messages
Fixed T = 24, no paddinglargest T keeping ≥ 50% of messages
Crop at T = 24 (kept as an ablation)cuts 24.6% of links (T = 64: 5.1%); 63% of messages sit in cut links (T = 64: 26%)
Crop + length buckets {8, 16, 32, 64} + mask (alternative)every message used; 26.3% padding; four shapes
Crop + pad every window to 64 + mask (in use)every message used; 71.0% padding; one shape
71.0%padding rows, fixed 64
26.3%padding rows, buckets
≈ 2.7×rows spent on padding vs buckets
Why fixed 64 nowOne input shape (64 × 13), one model config, standard batches; the extra compute is accepted. Length buckets stay one setting away: buckets = (8, 16, 32, 64) in pipeline/benign_gridsybil/encoder_input_T64.ipynb instead of (64,).
The mask makes padding invisiblez = masked mean of H; reconstruction, physics and contrastive losses on real rows only; TimesBlock padding from T = 64.
RejectedResampling / interpolation invents motion and breaks Δτ; backfill looks like a frozen-position attack; packing several links in one row lets TimesNet mix them.
Speaker note: Padding every window to 64 is the simplest setup: every batch has the same shape and the model needs one configuration. The price is that about 71% of rows are zeros, roughly 2.7 times the padding of the bucketed variant, which we accept. Bucketing (Khomenko et al. 2016, arXiv 1708.05604) remains the documented alternative. Cropping bounds the length, and random crops of long links can also serve as contrastive views (TS2Vec, AAAI 2022); masked pooling as in MOMENT, TimesFM, Chronos.

Caveats · Outliers

What a z-score is and what an outlier looks like

We rescale every feature to "how many standard deviations from the training average": z = (value − train mean) / train std. Most real values land between −3 and +3.

illustrative · claimed_pos_y (mean 645 m, std 387 m)
FeatureLargest |z|In real units
claimed_pos_y26.5≈ 10.9 km
claimed_pos_x20.2≈ 9.8 km
range36.5claim ≈ 12.8 km from the receiver (honest: median 81 m, p99 384 m)
log_dtau8.5gap ≈ 190 s since the pseudonym was last heard
An outlier is a value far outside the normal zone. Ours are mostly GridSybil ghost cars claiming far-away positions.
Speaker note: a z-score just says "how unusual is this value compared with training data". An honest car sits near zero; a ghost claiming a position 10.9 km out sits at z = 26.5 — nine times past the usual edge of ±3.
Caveats · Outliers

Should we clip outliers?

Clipping caps every z at a limit (e.g. ±10). Here the extreme values are the attack itself, so blind clipping throws away evidence.

illustrative · claimed_pos_y, clip at z = 10
log_dtau 8.5 = a ≈ 190 s gap before the same pseudonym was heard again. It is already on a log scale and is a real gap, not a bug — keep it.

Three options (none chosen yet):

  • log(range) — squeezes huge distances but keeps their order (far stays farther).
  • Robust scaling — use median / IQR instead of mean / std, so extremes do not stretch the scale.
  • Compare — train with and without clipping and report both.
Recommendation (proposal): do not clip by default. Use log(range), and run the with/without-clipping comparison so the choice is backed by results, not assumed.
Speaker note: clipping is a common reflex to stop huge values destabilising training, but here a ghost at 10.9 km would be squashed to look like one at 4.5 km — we would be hiding the very signal the detector needs. log(range) tames the scale without erasing the order, and the comparison run tells us whether clipping helps or hurts.
Caveats · ghost pseudonym 1

Ghost pseudonym 1: why it is a privileged grouping

Many GridSybil attackers send their ghosts under the same name, "pseudonym 1". We separated them using the true sender id, which a real car cannot see.

illustrative

  • The true sender id is only in the simulator logs, never an input feature.

Caveats · receivers across splits

Receivers repeat across splits — is that a leak?

Every message has two cars: the sender (who is benign or attacker) and the receiver (who just listens). We split by sender, so receivers can appear in train and test.

illustrative
  • The question is "is this sender lying?", so the split keeps each sender in one split only.
5,415of 5,421 test receivers also receive in train
No label leak. No sender vehicle is in two splits, so the model never sees a test sender's label during training.
But mild optimism. The receiver's own GPS track (rx_pos, rx_vel) appears in both train and test, so the model has seen those receiver paths before.
What to do (optional): a receiver-held-out check: test only on receivers never seen in train, and compare with the main score.
Speaker note: the label belongs to the sender, so splitting by sender is the right choice and nothing about the answer leaks. What does repeat is the listening car's own movement, which can make test scores slightly optimistic; a receiver-held-out check would measure how much.
Caveats · correlated samples

Correlated samples: why 376,427 windows are not 376,427 independent examples

Many windows repeat the same information, so the data holds less evidence than the window count suggests.

Why it matters: near-duplicate windows count as separate evidence, so metrics and their error bars look more certain than they really are.
What we do: evaluate grouped by sender vehicle. Group bootstrap = build confidence intervals by resampling whole vehicles, not single windows.
Speaker note: the window count overstates how much independent evidence we have, because one broadcast lands in several cars' windows and a long link is split into several windows. Caveats · class balance

Class balance: 35% benign, 65% GridSybil

With uneven classes, plain accuracy can reward a model that learned nothing.

The trap: a "model" that always answers "GridSybil" scores 65% accuracy while catching zero benign cars.
FixIn one line
Class weightsEach class's loss is scaled by its inverse frequency, so a benign mistake costs ≈ 1.4 and a GridSybil mistake ≈ 0.77 (illustrative rounding).
Macro-averaged metricsCompute the score per class, then take the plain average, so the smaller class counts as much as the larger one.
Always-GridSybil gets 65% accuracy but its macro-averaged recall is only 50% (100% on GridSybil, 0% on benign), which exposes the trick.
Speaker note: two-thirds of the windows are GridSybil, so accuracy alone is misleading; the constant "always GridSybil" answer already gets 65%. We weight the loss so both classes matter equally during training and report macro-averaged metrics so both classes matter equally in the results.
Caveats · Mask and padding

How the encoder must use the mask

Every window is filled up to 64 rows with zeros (71.0% of all rows). The mask says which rows are real, and every step of the model has to respect it.

illustrative
real [2, 4, 6] + padding [0, 0]
plain mean = 12 ÷ 5 = 2.4 (wrong)
masked mean = 12 ÷ 3 = 4.0 (right)
RuleWithout it
✓ Masked pooling: z = sum of real rows ÷ number of real rowsz is dragged towards zero; short windows look alike
✓ Losses on real rows onlythe model earns easy credit for "predicting" zeros
✓ TimesBlock padding computed from T = 64the period reshape no longer lines up with the input
✓ FFT periods from real rows only (built)the jump to zeros looks like a rhythm, so periods are fake
Speaker note: padding is just filler so every window has the same 64-row shape; here 59 of 64 rows are zeros; the mask tells the model which rows to ignore. The mean example is the whole story in miniature: averaging in zeros moves the answer from 4.0 to 2.4, and the same distortion happens in pooling, losses and the FFT unless each step uses the mask.
Caveats · Length shortcut

The length shortcut

A shortcut is an easy clue that predicts the label but has nothing to do with the real signal. Here the clue is how many messages a window holds.

Everyday version: telling wolves from huskies by spotting snow in the photo. It is often right, for the wrong reason, and fails on a wolf on grass.
  • The mask sum (= n_messages) gives away the length.
  • A classifier that sees only the number of real messages: AUC 0.531 (0.5 = chance). Weak, but real.
0.531length-only AUC (val)
0.5coin flip
What we do
  • Never feed n_messages or the mask as an input feature.
  • Keep a length-only baseline in every results table: the encoder must beat it.
  • Optional floor: min_messages = 4 drops the 1–3-message windows.
  • Windows with fewer than 4 real messages get period 1 in TimesNet anyway: too short for a rhythm.
Speaker note: GridSybil links are a bit shorter, so "short window" leans attack; a model could learn that instead of physics. At AUC 0.531 the clue is weak, so we do not hide the data; we refuse to hand length over as a feature and we always show the length-only score next to ours.
Encoder · overview

From window to vector: the encoder

A mask-aware TimesNet turns one 64 × 13 window into a vector per message (H) and one vector per window (z). Built in src/model/benign_gridsybil/timesnet_encoder_T64.ipynb; not trained yet.

top-3periods per window, from its real rows

Speaker note: the embedding turns the 13 features of each message into 128 numbers; four TimesBlocks then mix each message with its neighbours and with messages one rhythm earlier. H keeps one vector per message for the reconstruction and physics heads; z averages the real rows into one vector for the window, which the contrastive head and later the probes use.
Encoder · periods

How TimesNet finds rhythms (real rows only)

Each TimesBlock runs an FFT over a window's real rows only, keeps the 3 strongest frequencies f and turns each into a period: real rows ÷ f, rounded down.

What a period doesPeriod 7 folds the rows into lines of 7, so 2D convolutions see neighbours and the same moment one cycle earlier.
Short windows get period 1Under 4 real rows there is no usable frequency, so period 1 (24% of period choices).
Why real rows onlyZeros look like a rhythm. Synthetic test: true period found 10/10 (real rows) vs 9/10 (zero-padded FFT).
Speaker note: the bar heights are made up for the picture; the arithmetic is the real rule in the code (period = real rows divided by f, rounded down; f = 0 is the mean and f = 1 the whole window, so both are skipped). Each window gets its own three periods, and every block computes them again from its own input.
Encoder · mask

The mask inside the model

71% of all rows are padding. The mask enters at four places, so padding never changes H, z or a loss.

WhereWithout the mask
EmbeddingConv1d smears real rows into padding
TimesBlocksfake periods; padding fills with numbers
Poolingz pulled to 0 for short windows
Losseseasy credit for “predicting” zeros
Test: garbage in the paddingRandom numbers in the padding rows change H and z by exactly 0.
Losses (defined, not trained)Reconstruction scores the 25% of real rows it hides; P1–P3 use real rows; contrastive uses z.
Speaker note: the EDA showed why this matters: an unmasked mean already leaks length (log_dtau AUC 0.492 → 0.442). With the mask at these four places the model can only learn from the messages that were actually received.
